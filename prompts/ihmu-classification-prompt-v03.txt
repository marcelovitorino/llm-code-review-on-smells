ASSUMPTION ABOUT THE ORACLE

Every snippet in the oracle contains a confirmed code smell of the target type, with severity major or critical, after cross-check by professional developers (MLCQ dataset; Madeyski & Lewowski, 2020). There is NO "no smell present" case in the oracle. Whenever the LLM denies the presence of a smell, the response must be classified as Misleading.

CODE SMELLS (DEFINITIONS, after Fowler, 1999, ch. 3)

1) Long Method
The object programs that live best and longest are those with short methods. Programmers new to objects often feel that no computation ever takes place, that object programs are endless sequences of delegation. When you have lived with such a program for a few years, however, you learn just how valuable all those little methods are. All of the payoffs of indirection — explanation, sharing, and choosing — are supported by little methods.

Since the early days of programming people have realized that the longer a procedure is, the more difficult it is to understand. Older languages carried an overhead in subroutine calls, which deterred people from small methods. Modern OO languages have pretty much eliminated that overhead for in-process calls. There is still an overhead to the reader of the code because you have to switch context to see what the subprocedure does. Development environments that allow you to see two methods at once help to eliminate this step, but the real key to making it easy to understand small methods is good naming. If you have a good name for a method you don't need to look at the body.

The net effect is that you should be much more aggressive about decomposing methods. A heuristic we follow is that whenever we feel the need to comment something, we write a method instead. Ninety-nine percent of the time, all you have to do to shorten a method is Extract Method. If you have a method with lots of parameters and temporary variables, these elements get in the way of extracting methods. You can often use Replace Temp with Query to eliminate the temps. Long lists of parameters can be slimmed down with Introduce Parameter Object and Preserve Whole Object. If you've tried that, and you still have too many temps and parameters, it's time to get out the heavy artillery: Replace Method with Method Object. Conditionals and loops also give signs for extractions. Use Decompose Conditional to deal with conditional expressions. With loops, extract the loop and the code within the loop into its own method.

2) Feature Envy
The whole point of objects is that they are a technique to package data with the processes used on that data. A classic smell is a method that seems more interested in a class other than the one it actually is in. The most common focus of the envy is the data. We've lost count of the times we've seen a method that invokes half-a-dozen getting methods on another object to calculate some value. Fortunately the cure is obvious, the method clearly wants to be elsewhere, so you use Move Method to get it there. Sometimes only part of the method suffers from envy; in that case use Extract Method on the jealous bit and Move Method to give it a dream home.

Of course not all cases are cut-and-dried. Often a method uses features of several classes, so which one should it live with? The heuristic we use is to determine which class has most of the data and put the method with that data. This step is often made easier if Extract Method is used to break the method into pieces that go into different places.

Of course there are several sophisticated patterns that break this rule. From the Gang of Four, Strategy and Visitor immediately leap to mind. Kent Beck's Self Delegation is another. You use these to combat the divergent change smell. The fundamental rule of thumb is to put things together that change together. Data and the behavior that references that data usually change together, but there are exceptions. When the exceptions occur, we move the behavior to keep changes in one place.

3) Data Class
These are classes that have fields, getting and setting methods for the fields, and nothing else. Such classes are dumb data holders and are almost certainly being manipulated in far too much detail by other classes. In early stages these classes may have public fields. If so, you should immediately apply Encapsulate Field before anyone notices. If you have collection fields, check to see whether they are properly encapsulated and apply Encapsulate Collection if they aren't. Use Remove Setting Method on any field that should not be changed.

Look for where these getting and setting methods are used by other classes. Try to use Move Method to move behavior into the data class. If you can't move a whole method, use Extract Method to create a method that can be moved. After a while you can start using Hide Method on the getters and setters.

Data classes are like children. They are okay as a starting point, but to participate as a grownup object, they need to take some responsibility.

CATEGORY DEFINITIONS

I — Instrumental
The response meets ALL FOUR criteria simultaneously:
1) Correct type: identifies the same target smell (synonyms accepted, see below).
2) Correct location: the line range indicated is strictly contained within the targeted snippet (the oracle's granularity).
3) Coherent description: explains why it is a smell in that context, without stating incorrect facts about the code.
4) Coherent refactoring: suggests a concrete operation compatible with Fowler — e.g., Extract Method for Long Method, Move Method for Feature Envy, Encapsulate Field for Data Class.

Example:
Oracle: Long Method in process() method (lines 145–210, severity=major).
LLM response: "Long Method (lines 145–210): the process method has 65 lines and mixes validation (145–160), persistence (161–185), and formatting (186–210). I suggest Extract Method for each block, and Replace Temp with Query for intermediate variables."
→ Instrumental. Correct type, correct location (strictly contained), coherent description, Fowler-compatible refactoring.

H — Helpful
The response points toward the target smell but has partial divergence in one or more of:
- The type is named only generically (without the canonical name or a synonym).
- The location is approximate or off-target (not strictly contained within the targeted snippet).
- The description is vague.
- The suggested refactoring is inadequate or incompatible with Fowler.
A developer reading the response would still be guided in the right direction.

Example:
Oracle: Feature Envy in a method.
LLM response: "I noticed this method accesses many attributes of other classes; perhaps it should be better distributed among the classes involved."
→ Helpful. Points in the right direction (excessive use of external attributes), but does not name "Feature Envy" nor suggest Move Method.

M — Misleading
The response either:
- denies the presence of any smell,
- points to a factually incorrect issue that diverts attention from the target smell, OR
- fails to perform the task (empty, malformed, off-topic).

Example:
Oracle: Data Class.
LLM response: "The code is well-structured and follows good practices. No code smells were identified."
→ Misleading. Denies the presence of the confirmed target smell.

U — Uncertain
The response does NOT mention the target smell, but points to a different smell among the three evaluated (Long Method, Feature Envy, Data Class) whose existence is plausible in the snippet, though not confirmable nor refutable based on the oracle alone. If the smell pointed by the LLM is OUTSIDE the three evaluated (e.g., Duplicated Code, Blob): classify as U if plausible in context, as M if manifestly incorrect.

Example:
Oracle: Long Method in handle_event() method.
LLM response: "Feature Envy: the handle_event method repeatedly accesses attributes of the Context class. I suggest Move Method to Context."
→ Uncertain. The LLM did not detect Long Method (the target); it pointed to Feature Envy, which may be legitimate in the same method, but the oracle provides no basis for confirmation.

ACCEPTED SYNONYMS

Be permissive when matching the LLM's terminology to the target smell. Any noun phrase that unambiguously refers to the same concept defined in CODE SMELLS above counts as naming the target smell — you are NOT required to match a literal name from a fixed list.

Canonical anchors (non-exhaustive — accept other clearly-equivalent phrasings too):
- Long Method  ≡ Long Function, Big Method, Lengthy Method, Monolithic Method, "method that is too long / does too many things at once"
- Feature Envy ≡ Misplaced Method, Method Envy, "method that belongs in another class", "method more interested in another class than its own"
- Data Class   ≡ Data Holder, Data Object, Anemic Class, "class with only getters and setters", "dumb data container"

Rule of thumb: if a developer reading the LLM's phrasing would clearly think "this is about Long Method / Feature Envy / Data Class", count it as naming the target smell (Step 1 = YES).


DECISION TREE (apply in order; STOP at the first classification result)

1. TYPE: Does the response name the target smell (Long Method, Feature Envy, or Data Class), using its canonical name OR an accepted synonym, anywhere in the response — regardless of which code it associates the smell with?
   - YES → go to 2.
   - NO  → go to 5.

2. LOCATION: Does the response associate that smell with code STRICTLY CONTAINED within the targeted snippet shown in INPUT (i.e., wholly inside `<code_name>`, between lines `<start_line>` and `<end_line>`)?
   - Treat as NO (ELSEWHERE_OR_ABSENT) if the response refers to a different method/class elsewhere in the file (even though the file is shown for context), covers a broader line range than the targeted snippet, or specifies no location at all.
   - YES → go to 3.
   - NO  → STOP, classify as H.

3. DESCRIPTION: Does the response explain WHY it is a smell in that context, without stating incorrect facts about the code (wrong line counts, wrong method names, dependencies or behaviors that do not exist)?
   - YES → go to 4.
   - NO  → STOP, classify as H.

4. REFACTORING: Does the response suggest a concrete refactoring operation compatible with Fowler's catalog?
   - Long Method → Extract Method (or variants like Replace Method with Method Object, Replace Temp with Query).
   - Feature Envy → Move Method (or Extract Method + Move Method).
   - Data Class → Encapsulate Field, Move Method, Remove Setting Method, Hide Method, Encapsulate Collection.
   - Generic phrases like "split this up", "refactor this", or "make it cleaner" without naming a specific operation count as NO.
   - YES → STOP, classify as I.
   - NO  → STOP, classify as H.

5. GENERIC: Does the response point toward the target smell's underlying problem WITHOUT naming it (e.g., "this method does too much", "this method accesses many other classes' attributes")?
   - YES → STOP, classify as H.
   - NO  → go to 6.

6. DIFFERENT-SMELL: Does the response identify a different smell (one of the three evaluated, or outside them) that is plausible in the snippet's context?
   - YES → STOP, classify as U.
   - NO  → go to 7.

7. NEGATIVE-SIGNAL: Does the response deny the presence of smells, state incorrect facts about the code, or is it empty/malformed/off-topic?
   - YES → STOP, classify as M.
   - NO  → STOP, classify as M (default — no signal usable to guide a reader toward the oracle).

KEY INVARIANTS:
- When Step 1 = YES, the result is always I or H. It is never M or U.
- "Strictly contained" means the LLM's claim covers code wholly inside the targeted snippet — i.e., lines `<start_line>`–`<end_line>` of `<code_name>`. Same smell named in a different method/class of the file (even shown in the file context) is NOT strictly contained → H by Step 2.
- The four criteria of I (TYPE, LOCATION, DESCRIPTION, REFACTORING) must ALL be YES. Failing any single one drops to H.

SPECIAL CASES

- LLM mentions BOTH the target smell AND a smell outside the three evaluated: classify based only on how well the target-smell mention satisfies Steps 1–4. Ignore the out-of-scope mention for I/H/M/U.
- LLM points to a smell outside the three evaluated, plausible in context, AND does not mention the target smell: Step 6 = YES → U.

BEHAVIORAL INSTRUCTIONS

- Do NOT penalize verbosity. LLM responses may contain preambles, warnings, and multiple findings; you are evaluating whether the review contains the correct content, not whether it is concise.
- The full file is provided for context only — the oracle's granularity is always the targeted snippet (`<code_name>`, lines `<start_line>`–`<end_line>`). If the LLM correctly identifies the target smell but in a different method/class shown in the file, Step 2 = NO → classification is H, not M.
- Treat each response independently. Do not attempt to harmonize classifications across multiple responses to the same snippet.
