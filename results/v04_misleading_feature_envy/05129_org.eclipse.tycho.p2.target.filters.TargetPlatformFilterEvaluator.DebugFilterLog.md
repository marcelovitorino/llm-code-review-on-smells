**1. The `applyRestrictionFilter` method is doing too much at once**

The `applyRestrictionFilter` method is responsible for parsing patterns, logging, iterating over units, matching against two patterns, removing units, and logging the outcome for each unit. This method is handling multiple responsibilities: filter orchestration, pattern matching, and logging. The result is a method that is relatively long and difficult to follow, especially as the filtering logic grows or if additional logging/debugging is enabled in the future.

**Evidence:**
```java
private void applyRestrictionFilter(TargetPlatformFilter filter, Collection<IInstallableUnit> targetPlatformUnits) {
    ParsedCapabilityPattern scopePattern = parsePattern(filter.getScopePattern(), null);
    ParsedCapabilityPattern restrictionPattern = parsePattern(filter.getActionPattern(), scopePattern);

    filterLogger.beginEvaluation(filter);

    for (Iterator<IInstallableUnit> unitIterator = targetPlatformUnits.iterator(); unitIterator.hasNext();) {
        IInstallableUnit unit = unitIterator.next();

        if (matches(unit, scopePattern)) {
            if (!matches(unit, restrictionPattern)) {
                unitIterator.remove();

                filterLogger.unitRemoved(unit);
            } else {
                filterLogger.unitKept(unit);
            }
        }

    }

    filterLogger.endEvaluation();
}
```

**Why it matters:**  
Long methods that mix orchestration, business logic, and side effects (like logging) are harder to read, test, and maintain. Extracting the inner loop (the logic that decides whether to remove or keep a unit) into a helper method would clarify intent and make the code easier to extend or debug. See Fowler's "Extract Method" refactoring: https://refactoring.com/catalog/extractMethod.html

**Suggestion:**  
Extract the inner logic (matching and removal/keeping) into a private helper method, e.g., `processUnitForRestriction(...)`, and let `applyRestrictionFilter` focus on orchestration. This will also make it easier to test the filtering logic in isolation.

---

**2. The `ParsedCapabilityPattern` class is a data holder with some logic, but most logic is still outside**

The `ParsedCapabilityPattern` class encapsulates the pattern data and provides matching methods, which is good. However, the construction of these objects and the logic for parsing and defaulting is still handled externally (in `parsePattern` and the constructor), and the matching logic is only partially encapsulated. The rest of the filtering logic (e.g., which capability to match against in the unit) is still handled in the outer class.

**Evidence:**
- The `matches` method in `TargetPlatformFilterEvaluator` switches on the pattern type and then fetches the relevant capability from the unit, before delegating to `ParsedCapabilityPattern` for the actual match.

**Why it matters:**  
This split of responsibility means that knowledge of how to match a pattern to a unit is spread across both classes. Ideally, the pattern class would encapsulate all logic for determining whether a unit matches, reducing coupling and making the code easier to extend (e.g., to support new capability types).

**Suggestion:**  
Consider moving the logic for extracting the relevant capability/capabilities from the unit into the `ParsedCapabilityPattern` class, perhaps via a method like `boolean matches(IInstallableUnit unit)`. This would make the pattern class a more responsible owner of its own matching logic and reduce the need for the outer class to know about the details of each capability type.

**3. The `FilterLogger` and `DebugFilterLogger` classes are tightly coupled to the evaluator and lack clear separation**

Both logger classes are inner classes that rely on the outer class's `logger` field and are only used within the evaluator. While this is not inherently problematic, it does mean that logging logic is mixed with filtering logic, and the logger classes are not reusable or easily testable in isolation.

**Evidence:**
- Both classes access `logger` directly and are only instantiated in the evaluator's constructor.

**Why it matters:**  
Mixing logging and business logic can make it harder to change logging behavior independently of filtering logic. If more sophisticated logging is needed in the future (e.g., for debugging or auditing), it would be better to decouple these concerns.

**Suggestion:**  
Consider extracting the logger classes into separate top-level classes or interfaces, and inject them into the evaluator. This would allow for easier testing and extension of logging behavior.

**4. The `ParsedCapabilityPattern` class is not a pure data class, but its logic is minimal and could be expanded**

**Why it matters:**  
Data classes that do not own their own behavior tend to be manipulated in detail by other classes, leading to scattered logic and reduced cohesion.

**Suggestion:**  
As above, consider moving more of the matching logic into this class, so that it is responsible for determining whether a unit matches, given all the necessary context.
