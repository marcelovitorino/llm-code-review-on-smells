**Summary**

The `PigServer` class is the main entry point for programmatic interaction with Apache Pig. It encapsulates the lifecycle of a Pig session, including script registration, query execution, batch management, file operations, and resource cleanup. The nested `Graph` class manages the logical plan and script cache for a session or batch, handling parsing, plan construction, and execution state.

**Review Comments**

---

**1. Overly Long and Complex Methods**

Several methods in `PigServer` and its nested `Graph` class are quite lengthy and perform multiple, distinct responsibilities. For example:

- The `registerScript(InputStream, Map<String,String>, List<String>)` method in `PigServer` is responsible for reading the script, performing parameter substitution, initializing the script state, and then parsing and executing the script via `GruntParser`. This method could be decomposed into smaller, intention-revealing helper methods (e.g., one for reading and substituting, one for parser setup and execution). This would improve readability and maintainability, making it easier to reason about each step and to test them in isolation. See [Fowler: Extract Method](https://refactoring.com/catalog/extractMethod.html).

- The `Graph.registerQuery` method is particularly long and handles several concerns: script cache management, batch mode logic, validation, parsing, and (in non-batch mode) immediate execution. This makes the method difficult to follow and increases the risk of introducing bugs when modifying any part of it. Consider extracting the script cache management, validation, and execution logic into separate methods. This would clarify the flow and make each responsibility explicit.

---

**2. Methods Operating on Foreign Data**

Within the `Graph` class, several methods operate extensively on the internal state of the logical plan (`lp`) and its operators, sometimes manipulating them in ways that might be more appropriate for the plan or operator classes themselves. For example:

- The `buildPlan` method in `Graph` traverses and reconstructs logical plans, enqueues operators, and connects them based on dependencies. While this is arguably within the remit of a session-level orchestration class, the method also directly manipulates operator plans and expressions. If the logic for traversing and connecting operators grows or changes, it may be better suited to a dedicated plan builder or utility class, rather than being embedded in the session state.

- Similarly, `skipStores` and `removeToLoad` directly manipulate the logical plan's structure, including disconnecting and removing operators. If these operations are common or complex, consider moving them to the logical plan or operator classes, so that the logic for plan mutation is encapsulated with the data it affects.

---

**3. Data Holder Classes**

The nested `Graph` class is primarily a data holder for the logical plan, script cache, and related state. While it does contain behavior for managing the plan and script cache, much of its public interface is focused on exposing or mutating its internal data structures. This is not necessarily a problem, but it does mean that logic operating on the plan and script cache is tightly coupled to the `Graph` class. If the class continues to grow in responsibilities, consider refactoring to separate the data (e.g., script cache, plan state) from the behavior (e.g., plan construction, script parsing).

---

**4. Opportunity for Further Decomposition**

Some methods, such as `PigServer`'s constructor, perform a large number of initialization steps, including property setup, connection management, logging, and Hadoop integration (with reflection). While each step is necessary, the constructor could be decomposed into smaller private methods (e.g., `initializeLogging`, `initializeATS`, `initializeCallerContext`) to clarify the sequence of actions and make the constructor itself easier to read and maintain.

---

**5. Script Cache and Query Building Logic**

The script cache management in `Graph` (e.g., in `registerQuery` and `buildQuery`) is somewhat intricate, with logic for handling line numbers, batch mode, and incremental script construction. This logic is tightly coupled to the batch execution model, but it is not immediately clear to a reader how the cache is intended to be used or what invariants are maintained. Extracting the script cache management into a dedicated helper or encapsulating it more clearly within `Graph` would make the code easier to understand and modify.

---

**6. General Observations**

- While the class is large, it is not a pure data class; it does encapsulate significant behavior.
- There is no evidence of methods that are more interested in the data of other classes than their own (i.e., no clear "feature envy").
- The main concern is the size and complexity of some methods, which could be improved by further decomposition and encapsulation.

---

**Summary**

Overall, `PigServer` is a complex orchestration class, and its responsibilities are broad. The main opportunities for improvement are in decomposing long, multi-responsibility methods into smaller, intention-revealing helpers, and in considering whether some plan-manipulation logic would be better encapsulated elsewhere. These changes would improve readability, maintainability, and testability, and would help the codebase evolve more safely over time.
