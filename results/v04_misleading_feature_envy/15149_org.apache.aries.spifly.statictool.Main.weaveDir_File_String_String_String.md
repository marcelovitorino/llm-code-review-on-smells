**Summary**

The `Main` class is a command-line utility for processing OSGi bundles that use `java.util.ServiceLoader.load()`. Its main responsibility is to modify the bytecode of such bundles so that the Thread Context ClassLoader is set appropriately during service loading. The class orchestrates reading and unpacking JARs, weaving bytecode, updating manifests, and repackaging the bundles. It contains several static utility methods for file and JAR manipulation, manifest editing, and bytecode weaving.

**Review Comments**

**1. The `weaveJar` Method is Doing Too Much**

The `weaveJar` method is responsible for orchestrating the entire process of unpacking a JAR, checking and updating manifest headers, weaving bytecode, extending import packages, and repackaging the JAR. The method is over 60 lines long and contains multiple distinct responsibilities:

- Unpacking the JAR and reading the manifest.
- Determining which manifest header to process.
- Modifying manifest headers based on which header is present.
- Calling `weaveDir` to perform bytecode weaving.
- Extending the import package if necessary.
- Repacking the JAR.
- Cleaning up temporary files.

This makes the method difficult to read, test, and maintain. For example, the logic for updating the manifest headers (lines that remove or rewrite headers) is intermixed with orchestration logic, and the code for cleaning up the temporary directory is at the end, regardless of earlier failures.

**Why it matters:**  
Long methods with multiple responsibilities are harder to understand and modify safely. They also make it difficult to reuse or test individual steps in isolation. According to Fowler's refactoring catalog, such methods should be decomposed into smaller, intention-revealing methods.

**Suggestion:**  
Extract the following responsibilities into their own private methods:

- Manifest header processing (e.g., `processConsumerHeader`)
- Manifest header updating (e.g., `updateManifestHeaders`)
- Temporary directory cleanup (could be handled with try/finally)
- JAR unpacking and repacking

This would leave `weaveJar` as a high-level orchestration method, improving readability and maintainability.

**3. The `weaveDir` Method is Also Overly Complex**

The `weaveDir` method is responsible for:

- Processing the consumer header.
- Iterating over all files in a directory tree.
- For each `.class` file, reading, weaving, and writing the bytecode.
- Handling the bundle classpath and recursively weaving embedded JARs.

This method is over 50 lines and contains nested logic for file iteration, class name resolution, bytecode weaving, and error handling.

**Why it matters:**  
Packing all these steps into a single method makes it difficult to follow the flow and to isolate or reuse parts of the logic. For example, the logic for handling class files could be extracted, as could the logic for handling bundle classpath entries.

**Suggestion:**  
Extract the following into helper methods:

- Processing a single class file (e.g., `weaveClassFile`)

**4. The Class is a "God Class" Utility with No Cohesive State**

While this is common for command-line utilities, it means that all responsibilities—argument parsing, file I/O, manifest manipulation, bytecode weaving—are centralized in a single class.

**Why it matters:**  
Such classes tend to grow over time, accumulating more responsibilities and making it harder to maintain or extend. They also make it difficult to test individual behaviors in isolation, as everything is coupled together.

**Suggestion:**  
Consider splitting responsibilities into separate classes:

- A class for manifest/header manipulation.
- A class for file/JAR operations.

This would improve cohesion and make the codebase more maintainable.
