**1. The `listTable` Method Is Doing Too Much**

The `listTable` method is responsible for listing volumes referenced in both the tablets and deletes sections of a table, as well as current WAL logs. It performs several distinct operations in sequence:

- Scans the tablets section, extracting data file, log, and directory volumes.
- Prints the discovered volumes.
- Scans the deletes section, extracts and prints volumes.
- Queries the WAL state manager for current logs, extracts and prints volumes.

Each of these steps involves its own logic for scanning, parsing, and output. The method is over 50 lines long and contains multiple nested loops and conditionals. This makes it difficult to quickly understand what the method does at a high level, and increases the risk of introducing bugs when modifying any part of it.

**Why it matters:**  
Long methods that perform multiple responsibilities are harder to read, test, and maintain. They also make it more difficult to reuse or refactor individual pieces of logic. According to Fowler's refactoring catalog, methods should be aggressively decomposed into smaller, intention-revealing helpers (see [Extract Method](https://refactoring.com/catalog/extractMethod.html)).

**Suggestion:**  
Extract each logical step into its own private static method. For example:

- `listTabletsSectionVolumes(String name, ServerContext context)`
- `listDeletesSectionVolumes(String name, ServerContext context)`
- `listCurrentLogVolumes(String name, ServerContext context)`

This would make `listTable` a high-level orchestrator, improving readability and maintainability.

---

**2. Utility Methods Are Thin Wrappers Over Other Classes' Data**

Methods like `getTableURI`, `getLogURI`, and `getLogURIs` are simple wrappers that convert a string or object into a volume URI using `FileType` logic. While this is not inherently problematic, these methods are only delegating to another class's logic and do not encapsulate any domain-specific behavior of their own.

**Why it matters:**  
When utility methods exist solely to adapt or forward calls to other classes, it can be a sign that the logic might be better placed closer to the data it operates on. For example, if `LogEntry` or `Path` objects are always converted to URIs in this way, it may be more cohesive to provide this as a method on those classes.

**Suggestion:**  
Consider whether these conversion methods belong in this utility class, or if they would be better as instance methods on the relevant domain objects (e.g., `LogEntry.getVolumeURI()`). This would improve encapsulation and reduce the need for external classes to know about the conversion logic.

---

**3. The Class Is a Pure Utility With No State or Encapsulation**

`ListVolumesUsed` is a static utility class with no fields and only static methods. All logic is procedural and operates on data from other classes. The class itself does not encapsulate any state or behavior beyond orchestrating calls to other APIs and printing results.

**Why it matters:**  
While utility classes are sometimes necessary, overuse can lead to procedural code that is harder to extend or test. In this case, the class is essentially a script, and all domain logic is handled elsewhere. This is acceptable for a one-off tool, but if this logic grows or needs to be reused, it may be better to encapsulate responsibilities in dedicated classes.

**Suggestion:**  
If this utility grows in complexity, consider refactoring it into a set of collaborating objects, each responsible for a specific aspect of volume discovery or reporting.
