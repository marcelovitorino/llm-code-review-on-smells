**Summary**

`AclFileParser` is a utility class responsible for parsing ACL (Access Control List) configuration files into a `RuleSet` object. It provides methods to read from a file or URL, tokenize and interpret the ACL/config lines, and build up the rule set using a `RuleSetCreator`. The parsing logic is centralized in the `parse(Reader, EventLoggerProvider)` method, which orchestrates tokenization, line handling, and dispatches to helper methods for parsing ACL and config lines. The class is stateless and only exposes static methods.

**Review Comments**

---

**1. The main parsing method is overly long and complex**

The `parse(Reader, EventLoggerProvider)` method is responsible for the entire lifecycle of reading, tokenizing, and interpreting the ACL file. This method is over 100 lines long and contains multiple nested control structures, including a large `do-while` loop with a `switch` statement, and several blocks of logic for handling different token types and error conditions.

This makes the method difficult to follow and maintain. For example, the logic for handling line continuations, stack management, and dispatching to `parseAcl` or `parseConfig` is all interleaved. If a bug or new feature needs to be added (e.g., supporting a new keyword), it would be challenging to do so safely.

**Why it matters:**  
Long methods with multiple responsibilities are harder to understand, test, and modify. They tend to accumulate more local variables and temporary state, increasing cognitive load for readers and maintainers. According to Fowler's refactoring catalog, such methods should be aggressively decomposed into smaller, intention-revealing helpers (see [Extract Method](https://refactoring.com/catalog/extractMethod.html)).

**Suggestion:**  
Extract the following blocks into well-named private methods:
- The logic for handling a completed line (i.e., when `TT_EOL` or `TT_EOF` is encountered and the stack is not empty).
- The logic for handling continuation characters.
- The logic for pushing tokens onto the stack.
- The logic for error handling and reporting.

This would reduce the size of the main loop and make the control flow clearer.

---

**2. The parser method is responsible for too many details of token and stack management**

Within the main parsing loop, the method manages a `Stack<String>` to accumulate tokens for each line, handles line continuations, and interprets the meaning of the first token (number, ACL, CONFIG, etc.). This means the method is not only orchestrating the parsing process but also deeply involved in the mechanics of token accumulation and interpretation.

**Why it matters:**  
This violates the principle of single responsibility. The method is both a high-level orchestrator and a low-level token handler. This makes it harder to reuse or test the tokenization logic independently, and increases the risk of subtle bugs (e.g., off-by-one errors in line numbers, stack mismanagement).

**Suggestion:**  
Consider extracting the stack/token accumulation logic into a dedicated helper class or method. For example, a `LineTokenizer` could encapsulate the logic for reading a logical line (including continuations) and returning a list of tokens. The main parser could then focus on interpreting these logical lines.

---

**3. The class is not a data class, but the helper methods are tightly coupled to the data structures of other classes**

While `AclFileParser` itself is not a data class (it has no fields), its helper methods such as `parseAcl`, `parseConfig`, and `toRulePredicates` are tightly coupled to the internal structure of `RuleSetCreator`, `AclRulePredicates`, and other domain classes. For example, `parseAcl` directly manipulates the arguments list and passes them to `RuleSetCreator`, while `toRulePredicates` and `toPluginProperties` assume a very specific token structure.

**Why it matters:**  
This tight coupling makes the parser brittle to changes in the domain model. If the structure of ACL rules or config properties changes, multiple methods in this class will need to be updated. It also makes it difficult to reuse the parsing logic in other contexts.

**Suggestion:**  
Consider moving some of the parsing logic closer to the domain classes themselves. For example, `AclRulePredicates` could provide a static method to parse itself from a list of tokens, reducing the need for the parser to know about its internal structure.

---

**4. The method for parsing ACL rules is doing too much**

The `parseAcl` method is responsible for:
- Validating the number of arguments.
- Parsing the outcome and operation.
- Validating the rule number.
- Handling two different forms of ACL rules (with and without object/predicates).
- Creating and adding the rule to the `RuleSetCreator`.

This method could be decomposed further to separate validation, parsing, and rule creation.

**Why it matters:**  
Methods that do too much are harder to test and maintain. If the ACL rule format changes, this method will become even more complex.

**Suggestion:**  
Extract the logic for parsing the outcome, operation, and object/predicates into separate methods. This will make the code more modular and easier to extend.

---

**5. No evidence of feature envy or data class issues**

The class does not exhibit feature envy, as it does not operate extensively on the internals of other objects beyond what is necessary for parsing. It is also not a data class, as it contains only static methods and no fields.

---

**Summary**

The main concern with `AclFileParser` is the size and complexity of its main parsing method, which handles too many responsibilities and is difficult to follow. Extracting smaller, intention-revealing methods and delegating some parsing responsibilities to domain classes would improve maintainability and clarity. There are no significant issues related to feature envy or data class smells.
