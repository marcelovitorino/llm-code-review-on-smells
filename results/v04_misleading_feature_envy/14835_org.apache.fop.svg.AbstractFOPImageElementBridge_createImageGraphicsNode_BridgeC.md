According to Fowler's recommendations (see [Refactoring: Long Method](https://refactoring.com/catalog/extractMethod.html)), methods should be aggressively decomposed into smaller, intention-revealing helpers.

**Suggestion:**

- Image loading and conversion (e.g., `loadAndConvertImage`)
- SVG DOM handling (e.g., `handleSVGDOMImage`)
- Specialized node creation (e.g., `createSpecializedNode`)
- Viewport initialization (e.g., `initializeImageViewport`)
- Error handling and fallback

This would reduce the cognitive load for readers and make the orchestration logic in `createImageGraphicsNode` much clearer.

**2. The `createImageGraphicsNode` method is tightly coupled to image type details**

It also means that the method is more interested in the details of the `Image` subclasses than in its own class's responsibilities, which is a sign that some of this logic might belong elsewhere.

**Suggestion:**  
Consider introducing a strategy or factory pattern for image node creation, where each image type knows how to produce its own `GraphicsNode`, or where a registry maps image flavors to node creators. This would reduce the need for explicit type checks and central dispatch, improving extensibility and cohesion.
